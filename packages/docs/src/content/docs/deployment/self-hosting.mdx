Self-hosting gives you full control over your data, no rate limits, and the ability to customize the server. The default Docker stack includes **Redis** (event buffer), a **UI sidecar** (GHCR UI assets), and the **PizzaPi server** (relay API + web UI).

<Aside type="tip">
  This page covers the relay/server. Looking to run the **runner** (the agent host that connects out to a relay) in Docker instead? See [Runner Container](/PizzaPi/deployment/runner-container/).
</Aside>

---

## Quickest: `pizza web`

The fastest way to self-host is with a single command. No cloning, no config files — just Docker.

```bash
pizzapi web
```

This automatically:
1. Clones the PizzaPi repo (if not already present) to `~/.pizzapi/web/repo`
2. Generates required secrets (including `BETTER_AUTH_SECRET` and VAPID keys) and a Docker Compose file in `~/.pizzapi/web/`
3. Uses the GHCR UI image — the default tag matches the installed CLI version (falling back to `latest`) — or the local dev stack (`bun run dev` / `dev:ui`) when you run `--dev-ui` from a local checkout (UI on port 5173)
4. Builds and starts Redis + the relay server
5. Serves the web UI at **http://localhost:7492**

On subsequent runs, it pulls the latest repo changes, regenerates the compose file with the configured UI tag, and pulls the UI image before startup.

```bash
# Custom port (persisted for future runs)
pizzapi web --port 8080

# Set extra CORS origins (persisted)
pizzapi web --origins "https://example.com"

# Pull a specific GHCR UI tag (default is the installed CLI version)
pizzapi web --tag main

# Build the UI locally (fallback mode)
pizzapi web --build

# Run the local dev UI stack (repo checkout only)
pizzapi web --dev-ui

# Run in the foreground
pizzapi web --foreground

# View / change config without starting
pizzapi web config
pizzapi web config set port 9000
pizzapi web config set extraOrigins "https://example.com"

# Management
pizzapi web logs      # Tail container logs
pizzapi web status    # Show running containers
pizzapi web stop      # Stop the hub
```

All settings are persisted in `~/.pizzapi/web/config.json` and applied on every start. CLI flags like `--port` and `--origins` update the config automatically — you only need to pass them once.

Persistent data (SQLite database) is stored in `~/.pizzapi/web/data/`.

<Aside type="tip">
  `pizza web` is ideal for personal use or quick evaluation. For production deployments with custom domains and TLS, see the manual Docker Compose setup below. See the [CLI Reference](/PizzaPi/running/cli-reference/#pizzapi-web) for the full list of commands and config keys. Use `--build` for the old local-build fallback behavior. Use `--dev-ui` if you want the hot-reloaded dev stack (`bun run dev`, which includes `dev:ui`) from a local PizzaPi checkout.
</Aside>

## Manual Docker Compose

<Steps>
1. **Clone the repository**

   ```bash
   git clone https://github.com/Pizzaface/PizzaPi.git
   cd PizzaPi
   ```

2. **Generate required secrets**

   The provided `docker/compose.yml` generates a random `BETTER_AUTH_SECRET` on first start when it is unset and persists it in the `pizzapi-data` volume, so it survives container restarts. Direct server execution requires a stable explicit secret (at least 32 characters); multi-replica deployments must also configure the same stable secret for every replica. Configure stable VAPID keys if you use Web Push; Compose does not generate or persist them. `pizzapi web` generates and persists these automatically. To set a secret explicitly, or configure VAPID keys before first start:

   ```bash
   export BETTER_AUTH_SECRET=$(openssl rand -hex 32)
   # Optional: only if you use Web Push
   export VAPID_PUBLIC_KEY=...
   export VAPID_PRIVATE_KEY=...
   export VAPID_SUBJECT=mailto:you@example.com
   ```

3. **Start the stack**

   ```bash
   docker compose -f docker/compose.yml up -d
   ```

   This starts:

   | Service | Port | Description |
   |---------|------|-------------|
   | `redis` | — (internal) | Session state / pub-sub (host port 6379 is commented out) |
   | `ui` | — | Sidecar that copies the GHCR web UI assets into a shared volume |
   | `ntfy` | — | Self-hosted push relay; optional, configured for [native Android push](/PizzaPi/web-ui/preferences/#native-android-push) |
   | `server` | 7492 | Relay API + Web UI |

4. **Open the web UI**

   Navigate to **http://localhost:7492** — you'll see the PizzaPi interface.

5. **Create your account**

   The first time you visit, register an account. Then run `pizzapi setup` on your dev machine pointing to `http://localhost:7492`.
</Steps>

<Aside type="tip" title="Expose to the internet">
  To access your relay from the internet, put it behind a reverse proxy (nginx, Caddy, Traefik) with TLS. See the [HTTPS with Caddy](#https-with-caddy) section below.
</Aside>

## Environment Variables

Configure the server by setting environment variables in Docker Compose or your shell:

| Variable | Default | Description |
|----------|---------|-------------|
| `PORT` | `7492` | HTTP/WebSocket listen port |
| `BETTER_AUTH_SECRET` | Generated and persisted by the provided Docker Compose stack when unset | Signs sessions and API tokens; explicit values must be at least 32 characters. Direct server execution requires a stable explicitly configured secret, and multi-replica deployments must share the same stable secret. Generate with `openssl rand -hex 32`. |
| `VAPID_PUBLIC_KEY` | — | Web Push public key (with `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT`). Auto-generated by `pizza web`; must be set manually for compose/no-Docker or push subscriptions break on restart. |
| `VAPID_PRIVATE_KEY` | — | Web Push private key. |
| `VAPID_SUBJECT` | — | Web Push subject (`mailto:` or `https:` URL). |
| `PIZZAPI_REDIS_URL` | — | Redis connection URL, e.g. `redis://localhost:6379` |
| `PIZZAPI_BASE_URL` | `http://localhost:5173` | Public URL of the UI, added to CORS trusted origins |
| `PIZZAPI_EXTRA_ORIGINS` | — | Comma-separated extra trusted origins (e.g. a Tailscale URL). Added to CORS and WebSocket auth without hardcoding hostnames. Example: `https://myhost.ts.net,http://myhost.ts.net:5173` |

See [Configuration & Environment Variables](/PizzaPi/customization/configuration/#environment-variables) for the runner settings and [server source](https://github.com/Pizzaface/PizzaPi/tree/main/packages/server/src) for server options.

### Custom `docker/compose.yml` overrides

```yaml
# docker/compose.override.yml  (not committed — create locally)
services:
  server:
    environment:
      PORT: "8080"
      PIZZAPI_REDIS_URL: redis://redis:6379
    ports:
      - "8080:8080"
```

```bash
docker compose -f docker/compose.yml --profile dev up
```

| Service | Port | Description |
|---------|------|-------------|
| `redis` | 6379 | Redis |
| `dev` | 7492, 5173 | Bun dev server (API + Vite UI via `concurrently`) |

```bash
bun install
```

## Running Without Docker

If you prefer not to use Docker:

<Steps>
1. **Install Bun**

   ```bash
   curl -fsSL https://bun.sh/install | bash
   ```

2. **Start Redis**

   ```bash
   # macOS via Homebrew
   brew install redis && brew services start redis

   # Ubuntu/Debian
   sudo apt install redis-server && sudo systemctl start redis
   ```

3. **Install dependencies and build**

   ```bash
   bun install
   bun run build
   ```

4. **Run the server**

   ```bash
   cd packages/server
   export BETTER_AUTH_SECRET=$(openssl rand -hex 32)
   export PIZZAPI_REDIS_URL=redis://localhost:6379
   bun run start
   ```

   <Aside type="caution">
   `bun run start` requires `packages/server/dist/index.js` to exist. Run `bun run build` first if you have not already.
   </Aside>
</Steps>

## Database

The server uses **SQLite** (via Kysely) for user accounts and session metadata. The database file lives at `packages/server/auth.db` by default (non-Docker); Docker uses `/app/data/auth.db` (named volume `pizzapi-data`, or `~/.pizzapi/web/data/` for `pizza web`).

### Running Migrations

Migrations run automatically on server startup for both Docker and no-Docker paths. `bun run migrate` is optional if you want to run migrations manually or inspect the process.

### Backup

```bash
# Simple backup — safe to copy while the server is stopped
cp packages/server/auth.db packages/server/auth.db.backup
```

## Reverse Proxy Configuration

When PizzaPi runs behind a reverse proxy (like Caddy, nginx, or Traefik in Docker), the server needs to trust proxy headers to correctly identify the real client IP for rate limiting and other security features.

### Loopback Proxies (Auto-Detected)

If your reverse proxy is on the **same host** and connects to PizzaPi via loopback (`127.0.0.1`) — for example, a system-installed nginx or Caddy forwarding to `localhost:7492` — no configuration is needed. The server auto-detects this and safely trusts `X-Forwarded-For` headers.

:::caution[Docker Compose is not loopback]
In Docker Compose, **all inter-container traffic goes over a bridge network** (e.g. `172.x.x.x`), even when all containers run on the same machine. PizzaPi sees the proxy's bridge IP — not `127.0.0.1` — so the auto-detection does **not** apply. Docker Compose deployments with a reverse proxy always need `PIZZAPI_TRUST_PROXY=true` (see below).
:::

### Non-Loopback Proxies

If your reverse proxy reaches PizzaPi via a **non-loopback address** — a Docker Compose bridge, a Docker overlay network, a cloud load balancer, or anything else that isn't `127.0.0.1`/`::1` — you need to tell PizzaPi which peers are trusted to set `X-Forwarded-For`.

There are two settings, in order of preference:

#### Preferred: `PIZZAPI_TRUSTED_PROXY_CIDRS` (CIDR allowlist)

A comma-separated list of CIDR ranges (IPv4 or IPv6) whose peers are trusted as proxies. This is the only safe option when:

- The proxy has a **public IP** (cloud load balancers, CDNs).
- The server shares its private network with **untrusted hosts** (multi-tenant VPC, shared LAN, multi-app Docker bridge) — any of which could otherwise spoof their IP by sending `X-Forwarded-For` directly.

```bash
# Cloud LB with a fixed CIDR
PIZZAPI_TRUSTED_PROXY_CIDRS="203.0.113.0/24" pizzapi web

# Single-host LB
PIZZAPI_TRUSTED_PROXY_CIDRS="203.0.113.50" pizzapi web

# Multiple proxies (mix of IPv4 / IPv6, bare IPs default to /32 or /128)
PIZZAPI_TRUSTED_PROXY_CIDRS="10.0.0.0/8, 2001:db8::/32, 203.0.113.50" pizzapi web
```

Loopback (`127.0.0.1`, `::1`) is always trusted in addition to the allowlist — you don't have to enumerate it.

#### Convenience: `PIZZAPI_TRUST_PROXY=true` (private/loopback only)

Trusts `X-Forwarded-For` from **any** loopback or RFC1918/ULA private peer (`10.x`, `172.16–31.x`, `192.168.x`, `fc00::/7`, `fe80::/10`, `169.254.x`). Convenient for single-tenant Docker Compose where you control every container on the bridge network.

```bash
PIZZAPI_TRUST_PROXY=true pizzapi web
```

Or in `docker/compose.override.yml` (pass **both** compose files explicitly when using `-f`):

```yaml
# docker/compose.override.yml
services:
  server:
    environment:
      PIZZAPI_TRUST_PROXY: "true"
```

```bash
docker compose -f docker/compose.yml -f docker/compose.override.yml up -d
```

:::caution[Don't use `PIZZAPI_TRUST_PROXY=true` on shared networks]
If untrusted hosts share the private network with the PizzaPi server — e.g. multi-tenant VPC, shared corporate LAN, or a Docker bridge with other apps reachable by attackers — those hosts can spoof their IP by sending `X-Forwarded-For` directly. Use `PIZZAPI_TRUSTED_PROXY_CIDRS` instead, scoped to just your proxy's IP.
:::

:::tip[Precedence]
`PIZZAPI_TRUST_PROXY=false` disables proxy trust entirely (kill switch). Otherwise, if `PIZZAPI_TRUSTED_PROXY_CIDRS` is set it takes precedence over `PIZZAPI_TRUST_PROXY=true`.
:::

<Aside type="caution">
  Only enable proxy trust if you actually have a reverse proxy in front of PizzaPi. Enabling without a proxy lets clients spoof their IP and bypass rate limiting.
</Aside>

### Multi-Proxy Chains

By default, PizzaPi uses the **rightmost** `X-Forwarded-For` entry — the IP appended by the directly-connected proxy. This is safe against client spoofing for single-proxy setups.

If you have **multiple trusted proxy hops** (e.g. CDN → nginx → PizzaPi), set `PIZZAPI_PROXY_DEPTH` to the number of **intermediate** hops between the outermost trusted proxy and the real client:

```bash
# CDN + local reverse proxy = 1 intermediate hop
PIZZAPI_TRUST_PROXY=true PIZZAPI_PROXY_DEPTH=1 pizzapi web
```

Or with both compose files explicitly (required when using `-f`):

```yaml
# docker/compose.override.yml — CDN + local proxy = 1 intermediate hop
services:
  server:
    environment:
      PIZZAPI_TRUST_PROXY: "true"
      PIZZAPI_PROXY_DEPTH: "1"
```

```bash
docker compose -f docker/compose.yml -f docker/compose.override.yml up -d
```

| Depth | Topology | XFF entry used |
|-------|----------|----------------|
| `0` (default) | Single proxy (Caddy, nginx, Traefik) | Rightmost |
| `1` | CDN + local proxy (2 total hops) | Second from right |
| `N` | N+1 total trusted hops | N positions from the right |

:::note
`PIZZAPI_PROXY_DEPTH` counts **intermediate** hops, not total proxies. A single reverse proxy uses `depth=0` (the default). If in doubt, leave it unset.
:::

## HTTPS with Caddy

Caddy automatically provisions TLS certificates via Let's Encrypt:

```text
# /etc/caddy/Caddyfile
relay.example.com {
    reverse_proxy localhost:7492
}
```

```bash
sudo systemctl reload caddy
```

Then update your CLI config to use the secure URL:

```bash
pizzapi setup
# Relay server URL: https://relay.example.com
```

## Remote access with Tailscale HTTPS

For private access, install and sign in to Tailscale on the relay host, enable MagicDNS, then proxy the local relay with Tailscale Serve:

```bash
tailscale serve --bg http://localhost:7492
tailscale serve status
```

Use the HTTPS hostname shown by `tailscale serve status`. Add that exact origin (without a trailing slash) to the web hub's **extra origins** setting, then restart the hub. For `pizzapi web`:

```bash
pizzapi web config set extraOrigins "https://your-hostname.tailnet.ts.net"
pizzapi web stop && pizzapi web
```

Stop serving with `tailscale serve off`. Tailscale Funnel makes the service public; treat it as internet-facing and retain strong account authentication. See [Tailscale Serve documentation](https://tailscale.com/kb/1242/tailscale-serve/).

## HTTPS for tunnelled development servers

A tunnel lets a runner expose a local development port through the relay. By default, it uses a path-prefix URL; client-side single-page apps may not route correctly under that prefix. Set `PIZZAPI_TUNNEL_DOMAIN` on the relay to use a dedicated wildcard origin (`https://<opaque-label>.<domain>/`) with verbatim paths. Local development can use `t.localhost:7492`; a real hostname needs wildcard DNS (`*.<domain>`) pointing to the relay.

`pizzapi web` can add Caddy for wildcard TLS. For a private LAN/tailnet, `PIZZAPI_CADDY=1` uses a local CA that each viewing device must trust. To use a publicly trusted certificate, configure `PIZZAPI_CADDY_DNS_PROVIDER` and a narrowly scoped `PIZZAPI_CADDY_DNS_TOKEN`; Caddy uses DNS-01, so inbound port 80 is not required. Example:

```bash
PIZZAPI_TUNNEL_DOMAIN=https://t.example.com:8444 \\
PIZZAPI_CADDY=1 \\
PIZZAPI_CADDY_DNS_PROVIDER=cloudflare \\
PIZZAPI_CADDY_DNS_TOKEN="$TOKEN" pizzapi web
```

The tunnel URL itself is a bearer credential; do not publish it. Use a separate domain from the relay's cookie domain. Tunnel TLS configuration applies to tunnel origins, not the relay's own HTTPS endpoint. See [Tunnel Tools](/PizzaPi/features/tunnels/) for URL behavior and limitations.

## Security Hardening

PizzaPi includes several built-in security measures for production deployments.

### Response Headers

All server responses include security headers automatically:

- `X-Content-Type-Options: nosniff` — prevents MIME-type sniffing
- `X-Frame-Options: DENY` — prevents clickjacking (tunnel responses use `SAMEORIGIN` to allow same-origin iframing)
- `X-XSS-Protection: 0` — disables the legacy browser XSS filter (the recommended modern practice)
- `Referrer-Policy: strict-origin-when-cross-origin` — limits referrer leakage
- `Permissions-Policy` — restricts browser feature access

No configuration needed — these are applied to every response.

### Request Body Size Limits

The server enforces body size limits to prevent denial-of-service:

- **API routes**: 1 MB maximum
- **Attachment uploads**: 30 MB per file by default (configurable via `PIZZAPI_ATTACHMENT_MAX_FILE_SIZE_BYTES`); multipart body ceiling 50 MB

Requests exceeding these limits receive a `413 Payload Too Large` response.

### Redis Health Monitoring

The `/health` endpoint reports Redis and Socket.IO connectivity status. When Redis becomes unavailable, the web UI shows a **dismissable degraded-mode banner** with automatic retry. Sessions continue operating with reduced functionality (no cross-node relay, no event persistence) until Redis recovers.

## Web Push Notifications

The server supports browser push notifications for session events. Push is configured automatically with `pizza web`, which generates and persists VAPID keys. For manual Docker Compose or no-Docker deployments, set stable `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, and `VAPID_SUBJECT` values so subscriptions survive restarts.

### Native Android background push (ntfy)

This is separate from browser Web Push and is Android-only; iOS does not receive background push through this integration. The bundled Compose stack includes ntfy, but you must expose a dedicated HTTPS hostname (for example `push.example.com`) through your reverse proxy and configure the server's `PIZZAPI_NTFY_PUBLIC_URL` and `PIZZAPI_NTFY_PUBLISH_TOKEN`. The internal URL remains `http://ntfy`.

The bundled ntfy service defaults to deny-all. Provision an admin publisher and a token, then allow anonymous read-only access to the unguessable device topics:

```bash
# Repository Compose deployment:
COMPOSE=docker/compose.yml
# For `pizzapi web`, use instead: COMPOSE="$HOME/.pizzapi/web/compose.yml"
docker compose -f "$COMPOSE" exec ntfy ntfy user add --role=admin pizzapi-publish
docker compose -f "$COMPOSE" exec ntfy ntfy token add pizzapi-publish
# Copy the returned tk_... token into PIZZAPI_NTFY_PUBLISH_TOKEN
docker compose -f "$COMPOSE" exec ntfy ntfy access everyone 'pizzapi-*' read-only
```

Set `PIZZAPI_NTFY_PUBLIC_URL=https://push.example.com` and the publish token in the server environment (for the repository Compose file, its `.env`; for `pizzapi web`, export them before starting the hub). `pizzapi web` reads these values when it regenerates Compose, so provide them on each invocation or persist them in the environment that launches it. Proxy streaming requests to ntfy without buffering. Never publish device topic names: the topic is the read credential. If the ntfy settings are absent, browser push still works, but native Android push does not. See [Preferences & Notifications](/PizzaPi/web-ui/preferences/#native-android-push) for the client behavior.
