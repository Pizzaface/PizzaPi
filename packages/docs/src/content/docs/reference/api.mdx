The relay server exposes a REST-like HTTP API used by both the web UI and the CLI. Most endpoints require authentication via an **API key** (CLI) or **session cookie** (browser). The real-time event channel is Socket.IO; this page covers the HTTP surface only.

<Aside type="note">
  This is an internal API — it's used by the official clients. It may change between versions.
</Aside>

---

## Authentication

### API Key (CLI)

Pass your API key in the `x-api-key` header:

```http
x-api-key: <64-character hex key>
```

### Session Cookie (Browser)

The web UI uses cookie-based sessions managed by [better-auth](https://better-auth.com). Log in via `POST /api/auth/sign-in/email`.

## Health

### `GET /health`

Returns server status. No authentication required.

```http
GET /health
```

**Response:**

```json
{
  "status": "ok",
  "redis": true,
  "socketio": true,
  "uptime": 1234,
  "version": {
    "server": "0.80.3",
    "socketProtocol": 1,
    "buildTimestamp": "2026-07-09T00:00:00.000Z"
  }
}
```

<Aside type="note">
  `GET /status` and `GET /api/status` are aliases of `/health`. If Redis or Socket.IO is unavailable, `status` becomes `"degraded"`.
</Aside>

## Authentication Endpoints

Authentication is handled by **better-auth** at the `/api/auth/*` prefix. See the better-auth documentation for the full list of endpoints.

### `POST /api/register`

Register a new account or log in to an existing one and issue a CLI API key. Used by `pizzapi setup`.

**Rate-limited:** 5 requests per 15 minutes per IP.

**Request body:**

```json
{
  "name": "Jordan",      // Required for new accounts; omit for existing
  "email": "you@example.com",
  "password": "••••••••"
}
```

**Response:**

```json
{ "ok": true, "key": "a1b2c3d4e5f6..." }
```

Keys are 64-character hex strings generated with `crypto.randomBytes(32)`.

Spawn a new agent session on a runner.

**Auth:** API key or session cookie.

**Request body:**

## Triggers

**Tenant isolation.** Every Event is stamped with the authenticated publisher's
`source.userId`, and every Route carries an `ownerUserId` (stamped server-side
from the creating principal — client-supplied values are ignored). A Route only
matches Events whose `source.userId` equals its `ownerUserId`, so one user's
publish can never fire another user's session or spawn routes, and webhook
event types can't cross-fire between users even when their names collide.
`fireId` idempotency is likewise scoped per owner. The only exception is a
config-file Route (`PIZZAPI_ROUTES_FILE`) with no `ownerUserId`: it is
operator-level and matches all users. Legacy rows whose owner could not be
backfilled at startup match nothing (they're logged and remain deletable).

### `POST /api/events` — publish an Event

The one fire path (ADR-0002): publish an Event; Routes decide which sessions
receive it. A `target.sessionId` makes an implicit single-session route
(ownership-checked); without one, existing routes for the event type deliver.

**Auth:** API key (`x-api-key` header) or session cookie.

**Request body:**

```json
{
  "type": "github:pr_opened",           // namespaced event type
  "payload": { "repo": "my/repo" },      // arbitrary payload object
  "summary": "PR #12 opened",            // optional human-readable summary
  "fireId": "unique-if-retried",         // optional: idempotency + response correlation
  "target": {                            // optional: direct one-session delivery
    "sessionId": "sess_abc",
    "deliverAs": "steer",                // "steer" (default, interrupts) or "followUp" (queues)
    "wake": true                         // resume an offline target session
  },
  "source": { "kind": "service", "id": "github" }  // optional; defaults from auth
}
```

**Response:**

```json
{
  "ok": true,
  "eventId": "evt_abc123",
  "created": true,                       // false when fireId dedup hit
  "deliveries": [{ "deliveryId": "dlv_1", "sessionId": "sess_abc", "status": "delivered" }],
  "spawnedSessions": []
}
```

---

### `GET /api/events` — global feed

List published events. Query: `type`, `before` (ISO timestamp cursor), `limit`.

**Auth:** API key or session cookie.

**Scoping:** only events the caller can see — events they sourced (their own
sessions, or their own API identity) and events with a delivery into a session
they own. Other users' payloads never cross the boundary.

---

### `GET /api/events/{eventId}/deliveries`

List deliveries recorded for an event, ordered by update time.

**Auth:** API key or session cookie.

**Scoping:** only deliveries into sessions owned by the caller are returned. An
unknown event returns `404`; an existing event for which the caller owns no
target sessions returns an empty list.

**Response:**

```json
{
  "deliveries": [
    {
      "deliveryId": "dlv_abc",
      "eventId": "evt_abc123",
      "eventType": "github:pr_opened",
      "sessionId": "sess_abc",
      "routeId": "rt_abc123",
      "deliverAs": "steer",
      "status": "delivered",
      "createdAt": "2025-01-15T12:00:00.000Z",
      "deliveredAt": "2025-01-15T12:00:01.000Z"
    }
  ]
}
```

`routeId`, `deliveredAt`, `respondedAt`, `response`, and `expiresAt` are present
only when applicable. `status` is:

- `pending` — queued, the target session is not available (yet)
- `inflight` — emitted to an ack-capable session; waiting for its receipt
  acknowledgement (transient — settles to `delivered` on the ack, or back to
  `pending` on ack timeout/disconnect for re-delivery)
- `delivered` — handed to the session (ack-confirmed by the recipient, or
  legacy handoff for older CLIs)
- `responded` — the response contract was answered
- `escalated` — unanswered, re-routed up the escalation chain
- `expired` — TTL lapsed with no answer / no recipient

**Response:**


### `GET /api/routes` — list routes

Routes are subscriptions (ADR-0002): an event type + a target (a session, or a
spawn spec for auto-spawn listeners). Query: `eventType`. Only routes the caller
owns (or ownerless config/legacy routes they can manage) are returned.

Routes whose runner is dead — no registration for 7+ days and no live socket on
any relay node — carry `runnerDead: true` and `runnerDeadSince` (ISO date of
the last registration). Such routes can never fire; delete them individually or
with `DELETE /api/runners/{runnerId}/routes`.

**Auth:** API key or session cookie.

---

### `DELETE /api/runners/{runnerId}/routes` — bulk-delete a runner's routes

Delete every route stamped with the runner (spawn listeners via
`spec.runnerId`, session subscriptions/schedules via `target.runnerId`) and
emit an unsubscribe reconcile delta per session route. Config-origin routes
(read-only) and webhook routes (`rt_wh_*`, managed by the webhooks surface)
are skipped and counted. Intended for cleaning up after a dead runner.

**Auth:** API key or session cookie; the caller must own the runner (live state
or the durable owner record). Runners with no resolvable owner are cleanable by
any authenticated user.

**Response:**

```json
{ "ok": true, "removed": 4, "skipped": 1 }
```

### `POST /api/routes` — create a route

Subscribe a session to an event type (or register an auto-spawn listener).

**Auth:** API key or session cookie.

**Request body (session subscription):**

```json
{
  "eventType": "github:pr_opened",
  "target": { "kind": "session", "sessionId": "sess_abc" },
  "deliverAs": "followUp",               // "steer" or "followUp"
  "params": { "branch": "main" },        // optional, forwarded to the emitting service
  "filters": [                            // optional payload filters
    { "field": "repo", "value": "my/repo", "op": "eq" }   // "eq" | "contains"; add "caseSensitive": true for exact casing
  ],
  "filterMode": "and",                    // optional: "and" (default) or "or"
  "origin": "agent"                      // optional: "agent" or "ui"
}
```

**Request body (auto-spawn listener):**

```json
{
  "eventType": "github:pr_opened",
  "target": { "kind": "spawn", "spec": { "runnerId": "runner_a1b2c3", "promptTemplate": "Review this PR", "cwd": "/work/repo", "autoClose": true } },
  "deliverAs": "followUp"
}
```

**Response:**

```json
{ "ok": true, "route": { "routeId": "rt_abc123", "eventType": "github:pr_opened", "...": "..." } }
```

The `routeId` doubles as the subscription id: pass it to
`PUT/DELETE /api/routes/{routeId}` to update or unsubscribe.

---

### `PUT /api/routes/{routeId}` — update a route

Update params/filters, or re-own a schedule by changing `target.sessionId`
(the route keeps its id, so durable schedule state survives the move).

Target changes are re-validated like `POST`: a spawn target must reference a
runner owned by the caller (the fail-closed owner stamp is re-applied), and a
session target must be owned by the caller.

**Auth:** API key or session cookie.

---

### `DELETE /api/routes/{routeId}` — delete a route

Unsubscribe. Sessions that have ended remain manageable: authorization falls
back through the route's stamped runner owner, so a standing schedule is

## Webhooks

Webhooks allow external services to publish Events via HMAC-authenticated HTTP requests. Routes determine whether each Event is delivered to existing sessions, spawns new sessions, or both.

### `POST /api/webhooks/{id}/fire`

Fire a webhook — publishes a `webhook:<slug>` Event and delivers it through all matching Routes. A Route may target an existing session or spawn a new one, so a fire can reach multiple sessions. **No session cookie required** — authenticated via HMAC signature.

**Auth:** HMAC-SHA256 signature of the request body using the webhook's `secret`. Two modes are supported and auto-detected by header presence:

- **Legacy mode** (default): sign the raw request body and send only `X-Webhook-Signature`.
- **Enhanced mode** (replay-protected): sign `${timestamp}.${nonce}.${rawBody}` and include `X-Webhook-Timestamp` (ISO string or RFC3339) and `X-Webhook-Nonce` headers. The timestamp must be within a 5-minute window and the nonce must be unique per delivery.

**Headers:**

```http
X-Webhook-Signature: <hex-encoded HMAC-SHA256>
Content-Type: application/json
```

For enhanced mode, also include:

```http
X-Webhook-Timestamp: 2025-01-15T12:00:00.000Z
X-Webhook-Nonce: <unique nonce>
```

**Response:**

```json
{
  "ok": true,
  "eventId": "evt_abc123",
  "sessionIds": ["session_existing", "session_spawned"],
  "spawnedSessions": ["session_spawned"]
}
```

`sessionIds` contains every delivery target; `spawnedSessions` contains only
the sessions created by spawn Routes.

If the event type is filtered out:

```json
{ "ok": true, "filtered": true }
```

A reused nonce in enhanced mode returns `409` with `{ "error": "Webhook nonce has already been used" }`.

The webhook's spawn config (runner/cwd/prompt/model) is synced into a
deterministic route (`rt_wh_<webhookId>`) on every webhook create/update/delete,
so config edits always apply. If no route accepts the delivery (e.g. the runner
rejects the spawn), the fire returns `503` — senders should retry.

## Tunnel (HTTP Proxy)

The tunnel endpoints proxy HTTP requests to services running on the runner's localhost. This allows the web UI to access dev servers, databases, or any local service through the relay.

### `* /api/tunnel/{sessionId}/{port}/*`

Session-based tunnel proxy. All HTTP methods are supported (GET, POST, PUT, DELETE, PATCH, HEAD, OPTIONS).

**Auth:** Session cookie (must be the session owner).

The request is forwarded to `127.0.0.1:{port}` on the runner. HTML, JS, and CSS responses are rewritten to route absolute paths through the tunnel prefix. Auth headers (`Cookie`, `Authorization`, `x-api-key`, `Referer`) and hop-by-hop headers (`Host`, `Accept-Encoding`, etc.) are stripped before forwarding. `apiKey` and `tunnelToken` query parameters are removed from the forwarded URL.

---

### `* /api/tunnel/runner/{runnerId}/{port}/*`

Runner-based tunnel proxy (preferred). Same as above but addressed by runner ID instead of session ID, making the URL stable across session restarts.

**Auth:** Session cookie (must own the runner).

The request is forwarded to `127.0.0.1:{port}` on the runner. HTML, JS, and CSS responses are rewritten to route absolute paths through the tunnel prefix. Auth headers (`Cookie`, `Authorization`, `x-api-key`, `Referer`) and hop-by-hop headers (`Host`, `Accept-Encoding`, etc.) are stripped before forwarding. `apiKey` and `tunnelToken` query parameters are removed from the forwarded URL.
